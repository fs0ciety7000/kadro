## Verdict

**Aucun bloquant** ; 6 importants, 12 mineurs. Aucune valeur de secret trouvée dans stdout, stderr, JSON, libellés ni
attributs. Refus sans prompt, pas de repli `plain`, pas de réutilisation d'entrée, rollback d'import : en place.
Restent des preuves (tests) et des exigences du modèle non livrées (vidages mémoire, `doctor`).

Commandes : `KROPA_REQUIRE_KEYRING_TESTS=1 cargo nextest run -p kropa-store -p kropa --locked` → 119 réussis, 5
ignorés (`inner_*`, lancés par les tests externes sous `dbus-run-session` + vrai `gnome-keyring-daemon`) ; `cargo deny
--locked check` ok ; `zizmor --offline` : rien ; crates.io : `secret-service` 5.2.0 dernière stable (6.0.0-rc.1).

## Écarts signalés : avis

1. **`secret-service` au lieu de `keyring`** : accepté. Vérifié dans la source : `Session::new_blocking` en `Dh` sans
   repli `plain`, `search_items` n'ouvre rien, `unlock` seulement après `may_prompt` (`secret_service.rs:225`).
2. **Un élément par secret** : accepté sous Linux (une lecture ne déchiffre qu'un secret, aucune
   lecture-modification-écriture d'un document commun) ; lien clé ↔ attributs (`document.rs:138-145`) testé
   (`gnome_keyring.rs:447-461`). Coûts : pas de verrou (M10), vides non comptés (M5). **macOS : I5.**
3. **RUSTSEC-2026-0370/-0371/-0372** : acceptables, conditions plus bas.
4. **Non-interactivité, délais, threads** : code correct ; preuve insuffisante (I1, I2), après délai (I6), SSH (M7).
5. **Saisie** : conforme (4 Kio, UTF-8, un seul `\n`, octet par octet sans dépasser la ligne, `Zeroizing`, fd 1 et 2
   refusés `args.rs:719-724`) ; restes M1 à M4.
6. **`profile_exists`, `status`, `--json`** : sans déverrouillage, vérifié sur gnome-keyring (`gnome_keyring.rs:523`) ;
   `status` = noms de profils et compteurs. `--json` muet au succès de set/remove/allow : cohérent avec `cli.md` § 4
   (pas de schéma propre), à écrire au § 2.4. Restes M5, M11.
7. **Import et limites** : rollback testé (`secrets_cli.rs:932`), `put` refuse l'existant, `set` garde origines et
   emplacements (`gnome_keyring.rs:266-279`), `allow` interactif seulement (`secrets.rs:414`). Restes I6, M9.

## Bloquants : aucun

## Importants

**I1. Le test « aucun prompt » ne le prouve pas** — `tests/gnome_keyring.rs:511-519`. Ici un prompt est rejeté
aussitôt (`inner_locked_prompt_unanswered` : < 6 s, `keyring_locked`) : un code qui appellerait `Unlock` sans TTY
passerait les mêmes assertions. *Correctif* : exiger le texte `no way to ask` et, surtout, un moniteur
(`BecomeMonitor`) sur le bus privé qui relève zéro appel `Unlock`/`Prompt` (test du § 7).

**I2. Branchement de `set_interactive` non testé** — `kropa-cli/src/lib.rs:251-255`. Seul contrôle contre un prompt
dans un script ; `MemorySecretSource` l'ignore. *Correctif* : magasin espion, matrice TTY × `--no-input` ×
`WAYLAND_DISPLAY`/`DISPLAY` ; `true` seulement avec TTY, affichage et sans `--no-input`.

**I3. Vidages mémoire non protégés** — § 6 (Q8) : `PR_SET_DUMPABLE 0` et `RLIMIT_CORE 0` « dans `kropa` dès qu'il
tient un secret », vrai depuis 1.8 ; rien n'est fait, aucun lot ne le porte. *Scénario* : Ctrl-\ pendant la saisie ou
plantage dans du C (aws-lc) → core avec le jeton chez `systemd-coredump`/apport. *Correctif* : `rustix::process::`
`set_dumpable_behavior` et `setrlimit(Core, 0)` (API sûres, fonction `process`) au démarrage hors `debug_assertions`,
test sur `/proc/self/status`.

**I4. `doctor` ne dit plus rien des secrets** — `doctor.rs:23` : la ligne « lot 1.8 » est retirée sans section
ajoutée, alors que `cli.md` § 2.8 promet le magasin, § 2.1 les doublons, N2 les orphelins. *Correctif* : bloc tiré de
`status()` (état, doublons) + profils du magasin absents de la config (noms seuls), ou remettre la ligne « à venir ».

**I5. Contrat macOS « un élément par secret »** — `broker.rs:14`. Au trousseau à fichier, ACL et partition
`cdhash:` sont **par élément** : N secrets = N invites à chaque mise à jour, contre une seule visée par Q5/U1. À
trancher par l'utilisateur avant 1.8m : document unique sous macOS (`document::decode`, qui refuse plus d'une entrée,
change alors) ou N invites assumées et dites. Non vérifié sur machine (1.6).

**I6. Issue inconnue après `keyring_timeout`** — `secret_service.rs:113-145`, `dest.rs:462-466`. Le thread abandonné
peut finir `CreateItem`/`Delete` après le rapport d'échec ; une entrée créée tard échappe au rollback, et `let _ =`
(`dest.rs:465`) tait l'échec du rollback. *Correctif* : message « a peut-être abouti, voir `kropa secrets status` »
(`en.ftl:402`, `fr.ftl:402`) ; rollback qui nomme les entrées restées (code 7) ; pas de ce modèle dans le résident
(2.1, 4.7) sans annulation (fermeture de connexion, `Prompt.Dismiss`).

## Mineurs

- **M1** `--secret-stdin`/`--secret-fd 0` sur un TTY : écho du jeton (`secret_input.rs:97`) → saisie masquée ou refus.
- **M2** fd ni `CLOEXEC` ni fermé (`secret_input.rs:12-14, 105-107`), contre § 3.7 ; inoffensif tant que `kropa` ne
  lance rien, à régler avant 2.1 : `unsafe` justifié ou limite écrite (décision de l'utilisateur, règle 12).
- **M3** Ctrl-C pendant la saisie laisse l'écho coupé (`secret_input.rs:110-143`) → `signal-hook` qui restaure.
- **M4** `/dev/fd/N` rouvre : un socket échoue (ENXIO, code 15), un fichier est relu depuis 0 → à dire (`cli.md` § 1).
- **M5** `empty` toujours 0 au trousseau (`secret_service.rs:435`) : « dont 0 encore vides » faux après import →
  `null`/« inconnu », ou attribut non secret `state=empty|set`.
- **M6** Service sans DH rendu « injoignable » (`secret_service.rs:190-193`) → distinguer `NotSupported` ; le test
  d'un service sans DH (§ 8) manque (faux service zbus, comme pour le portail).
- **M7** SSH avec `DISPLAY` transféré : prompt sur la console ou attente de 120 s (`lib.rs:253`) → `SSH_CONNECTION`
  vaut « sans affichage » pour le trousseau.
- **M8** `dest show` fait `load` (`dest.rs:97-104`) : déchiffre, voire un prompt, pour une présence → attributs seuls.
- **M9** `put` sur une entrée existante → `secret_store_error`, code 7 (`secret_service.rs:379`) → raison dédiée.
- **M10** Sans verrou, `set` et `allow` simultanés perdent une mise à jour ; deux créations font un doublon
  (`keyring_ambiguous`, côté sûr). Accepté, à écrire au § 3.4.
- **M11** `profile_exists` sur KeePassXC/ksecretd verrouillé : éléments peut-être tus (non vérifié) ; N2 en dépend,
  conséquence bornée (collision → doublon refusé).
- **M12** `kropa-store` ne revalide pas les identifiants avant `"{profile}/{name}"` (`document.rs:103, 138`) : refuser
  `/` et les contrôles dans le magasin aussi (défense en profondeur).

## Exceptions RUSTSEC (écart 3)

Acceptées : `informational = "unmaintained"`, `patched = []`, aucune faille ; seules ces trois ID sont ignorées, un
avis de faille sur zbus 5 / zvariant 5 casserait donc la CI. **Retrait** : dès `secret-service` 6.0.0 stable (zbus 6,
déjà dans l'arbre en 6.2.1) ; revue au plus tard le 28/02/2027, et sans stable : client direct sur zbus 6 (OpenSession
DH, SearchItems, Unlock, Prompt, GetSecret, CreateItem, SetSecret, Delete). **Retrait immédiat** si une faille touche
zbus 5, zvariant 5 ou zbus_names 4 (aucun correctif 5.x à attendre). `deny.toml:49` : remplacer « (to do) » par ce
fichier et ces conditions.

## Fuites de valeurs : vérifié

Libellé `Kropa: <profil>/<nom>` et attributs (`gnome_keyring.rs:315-342`) ; erreurs de document fixes, messages
`serde_json` jetés (`document.rs:41-60, 134`) ; `map_error` ne cite que des erreurs D-Bus ; `SecretValue` en `***`
(donc `Record`, `NewSecret`) ; invites et notes : noms, origines, emplacements ; JSON d'import : `has_value` ; binaire
réel contrôlé sur stdout + stderr (`keyring_cli.rs`). Rien trouvé. Copies restantes : `Vec` de `get_secret`
(`Zeroizing`), tampon `serde_json` d'une chaîne échappée ; sur le bus, chiffré (DH).
